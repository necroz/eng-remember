# Результаты код-ревью eng-remember (2026-11-14)

Спецификация для плана исправлений. Ревью проведено четырьмя параллельными ревьюерами
(домен/сервисы, bot-слой, LLM-подсистема, данные/инфраструктура); Critical и ключевые
Important проверены координатором лично. Объективные проверки на момент ревью: ruff ✅,
mypy strict ✅, 767 юнит-тестов ✅, 16 интеграционных (Postgres 17) ✅.

Обозначения: **C** — Critical, **I** — Important, **M** — Minor, **U** — улучшение.
Каждый пункт имеет идентификатор, на который ссылается план.

## Critical

- **C1. Невозвратная блокировка вернувшегося пользователя.**
  `bot/middlewares/user.py:64-66` + `services/reminders.py:289`: `is_blocked=True` ставится
  при недоставленном напоминании; `set_blocked(False)` не вызывается нигде. `/start`
  проходит через middleware, но флаг не сбрасывается — все последующие сообщения молча
  игнорируются. Фикс: сбрасывать `is_blocked` при любом входящем событии от пользователя
  (факт сообщения доказывает доставляемость) + тест полного цикла возврата.

- **C2. Утечка LLM-клиента: новый `AsyncOpenAI` на каждый апдейт, `aclose()` не вызывается.**
  `bot/middlewares/db.py:39` → `services/llm/factory.py:46` → `client.py:301`.
  Следствие той же природы: «знание» об отказах провайдера (`reasoning_effort`,
  `response_format`) живёт в per-request клиенте; дефолт `reasoning_effort="none"`
  (`config.py:87`) не поддерживается `gpt-4o-mini` → лишний 400+ретрай на каждом запросе.
  Фикс: process-wide транспорт (один пул + изученные флаги на процесс), per-request —
  только audit-sink с сессией; не слать `reasoning_effort` по умолчанию.

## Important

- **I1. Исходящие сообщения не защищены от лимита 4096.**
  `import_preview` рендерит все драфты без капа (`bot/texts.py:526-569`); `deck_list`
  (до 1000 колод после CSV-импорта, удаления нет); `paused_list`; `discovery_preview`;
  `explain` — у `ParseResponse.answer` нет лимита длины (`schema.py:372-375`, единственное
  свободное поле без валидатора). Фикс: централизованный safe-send/edit + капы рендера.

- **I2. Guard'ы конфликтуют с FSM.**
  Dedup (`middlewares/dedup.py:52-66`, TTL 60 с) отклоняет одинаковые ответы на разные
  карточки и повторные нажатия меню-кнопок; rate limit 10 сообщ/мин (`config.py:42-46`)
  ломает сессию 15–20 карточек при темпе быстрее ~6 с/карточку; устаревшие кнопки capture
  (`capture.py:577-586, 661-665, 542-558, 617-659`) не проверяют FSM и убивают активный
  review. В хендлер-тестах guard'ы отключены (`conftest.py:150-154`). Фикс: FSM-aware
  dedup/rate-limit, единый stale-guard, тесты с включёнными guard'ами.

- **I3. Напоминания обещают работу, которой нет.**
  `queue_counts` (`repositories/cards.py:266-277`) считает все новые карточки без вычета
  дневного бюджета; очередь (`services/review.py:126-143`) бюджет учитывает. Пользователь
  с выбранным лимитом ежедневно получает «Ждут: новых — N» → «повторять нечего».
  Фикс: единое правило «сколько новых доступно» для очереди, stats и тика.

- **I4. Дайджест теряется при первом тике после вечернего часа в день дайджеста.**
  `domain/reminders.py:81-82`: вечерняя ветка замыкает до проверки дайджеста.
  Фикс: приоритет дайджеста в его день + тест «первый тик вечером понедельника».

- **I5. Гонки целостности данных.**
  (а) `get_or_create` users/decks/streaks — check-then-insert без upsert → `IntegrityError`
  при параллельных первых апдейтах. (б) Дедуп регистронезависимый (`func.lower`), а
  unique-индекс регистрозависимый (`models/card.py:60-67`) — «run»/«Run» оба вставятся;
  `lower(term)` не использует индекс. (в) Запись расписания без оптимистичной блокировки
  (`services/review.py:162-201`) — двойной ответ сдвигает FSRS на один шаг вместо двух.

- **I6. Ширина колонки ≠ лимит схемы.**
  `part_of_speech`: `String(32)` (`models/card.py:88`) vs лимит 40 (`schema.py:61`);
  LLM-путь только strip'ит (`repositories/cards.py:87-91`) → `StringDataRightTruncation`
  и откат всего пакета. Фикс: согласовать лимиты + обрезка в `CardDraft.normalized()`.

- **I7. Эксплуатация тика и пула.**
  (а) Тик напоминаний — одна транзакция на проход (`__main__.py:146-149`), докстринг
  обещает обратное; crash → повторные напоминания + row-locks через сетевой I/O.
  (б) Пул 5+10=15 < `tasks_concurrency_limit=20` + фоновые задачи; соединение удерживается
  через LLM-вызов до 120 с. (в) `User.decks`/`User.streak` `lazy="selectin"` грузятся на
  каждый апдейт, но не используются. (г) `count_cards_introduced_since` сканирует всю
  историю ответов на каждое построение очереди.

- **I8. Алерты глобального бюджета — один раз за жизнь процесса.**
  `budget.py:36-61`: флаги не сбрасываются; `reset()` не вызывается и обнуляет notifier.
  Фикс: сброс флагов при спаде расхода ниже порога, notifier не трогать.

- **I9. Безопасность и деплой.**
  (а) Нет фильтра приватных чатов — в группе catch-all разбирает любые сообщения,
  `/stats` показывает личные данные. (б) CSV скачивается целиком (до 20 МБ) до проверки
  размера 1 МБ (`files.py:100-104`). (в) `docker/postgres-init.sql:5` хардкодит `OWNER eng`;
  дефолтные креды `eng/eng`, порт на `0.0.0.0`, `POSTGRES_*` нет в `.env.example`.

## Улучшения

- **U1.** Structured outputs (`json_schema`, strict) с детектом поддержки через
  существующий BadRequest-learning.
- **U2.** Retention `llm_calls` (квотам нужно только 24ч-окно); автобэкап вместо ручного
  `pg_dump` в доках.
- **U3.** Наблюдаемость: метрики тика и пула, алерт на `reminder_tick_crashed`, heartbeat,
  повторные алерты бюджета (часть I8).
- **U4.** Тесты с включёнными guard'ами + entrypoint-тесты (часть I2, M31).
- **U5.** Продуктовые мелочи: управление колодами (переименовать/удалить), редактирование
  карточек, фидбек на нетекстовый контент (часть M3), согласованный `/help` (часть M5).
- **U6.** Per-user семафор перед LLM-тяжёлыми хендлерами (один аккаунт не занимает все
  слоты конкурентности).
- **U7.** Связать дефолты пула и конкурентности, документировать в `.env.example`.

## Осознанные ограничения (не исправляем, документируем)

- `updated_at` поддерживается только ORM — приемлемо, триггер не добавляем.
- Полная casefold-эквивалентность в SQL (ß → ss) не достигается функциональным индексом
  `lower(term)` — документируем как ограничение; Python-пути унифицируем на casefold.
- Таблица `reviews` хранится бессрочно (нужна для истории и «первых ответов»);
  деградация запроса лечится индексом, не retention.
- Семантика «60 вызовов = 60 provider-запросов (включая ретраи)» — документируем.
