# eng-remember — исходный дизайн проекта

Дата: 2026-10-12
Статус: исторический документ. Актуальное состояние и список возможностей — в [README](../../../README.md).

## Задача

Telegram-бот для запоминания английских слов с интервальным повторением.
Пользователь пишет боту обычным текстом, бот разбирает сообщение через LLM,
сохраняет карточки в базу и дальше показывает их к повторению по расписанию,
которое считает алгоритм FSRS.

Задача расширена: человек добавляет слово, которое хочет запомнить, и может
запросить ещё слова из этого домена или связанные контекстом; ЛЛМ распознаёт
запрос, при необходимости задаёт уточнение — словами или просьбой прислать абзац
текста, из которого он найдёт ещё десяток слов. На повторении нужна геймификация:
серии, пропуски, заморозки. После удачного ответа — похвала на одно-два
предложения, причём вариантов должно быть много и повторяться они не должны
долго.

Сделано: каркас и обвязка плюс четыре подсистемы — подбор слов с диалогом
уточнений, серии с заморозками, банк похвал и напоминания. Озвучка, импорт из
файлов, экспорт и веб-панель по-прежнему не делались.

## Решения и почему именно так

Каждое решение ниже можно поменять; всё, что меняется без правки кода, вынесено
в переменные окружения.

| Решение | Почему |
|---|---|
| Python 3.12 + aiogram 3 | Самый распространённый стек для TG-ботов в русскоязычной среде: много примеров, async из коробки, живая экосистема. Если позже понадобится веб-панель — рядом встаёт FastAPI. |
| PostgreSQL + Alembic | Прод-готово с первого дня: конкурентная запись, `json`, `timestamptz`, настоящие каскады. SQLite поддерживается как режим разработки и тестов, но не как продакшн-вариант. |
| SQLAlchemy 2.0 async + репозитории | Все SQL-запросы живут в `repositories/`. Сервисы оперируют доменными объектами, обработчики бота вообще не знают про запросы. |
| FSRS (py-fsrs) | Современный алгоритм (тот же, что в новом Anki): считает вероятность вспоминания и подбирает интервал под целевую вероятность. Точнее классического SM-2 при том же объёме кода. |
| OpenAI-совместимый клиент | Один клиент работает с OpenAI, OpenRouter, DeepSeek, vLLM и локальным Ollama — меняются только `LLM__BASE_URL`, `LLM__API_KEY` и `LLM__MODEL`. Смена провайдера не требует правки кода. |
| Правила-фолбэк без LLM | Бот полностью работоспособен без ключа: понимает строки вида `word — перевод`. Это же позволяет гонять весь тест-сьют без сети. |
| Подтверждение перед сохранением | Разбор моделью может ошибиться. Показать результат и сохранить только по нажатию — дешевле, чем потом чистить чужие карточки. |

## Архитектура

Зависимости направлены строго в одну сторону: `bot → services → repositories → db`,
и `services → domain` без обратной связи.

```
eng_remember/
├── config.py          настройки (pydantic-settings, вложенность через __)
├── errors.py          иерархия исключений от одного корня
├── logging_setup.py   structlog: читаемый консольный или JSON
├── domain/            ЧИСТЫЙ домен: ни БД, ни Telegram, ни сети
│   ├── enums.py       ReviewRating, CardState (значения совпадают с py-fsrs)
│   └── srs.py         обёртка над py-fsrs, отдаёт CardSchedule
├── db/                база, движок, UtcDateTime, session_scope
├── models/            таблицы SQLAlchemy
├── repositories/      все SQL-запросы проекта
├── services/          сценарии: карточки, повторение, LLM
│   ├── llm/           клиент, схемы, промпты, парсер, фолбэк
│   └── container.py   единая сборка зависимостей на запрос
└── bot/               Telegram: роутеры, middleware, клавиатуры, тексты
```

Ключевые границы:

- **`domain/srs.py` — единственный модуль, знающий про py-fsrs.** Наружу отдаёт
  `CardSchedule` — dataclass, который один в один ложится на колонки `cards`.
  Планировщик — чистая функция от `(состояние, оценка, момент времени)`, поэтому
  интервалы проверяются тестами без базы и без бота.
- **LLM-клиент не знает про базу.** Каждая попытка сообщается через колбэк-сток,
  поэтому таблица аудита остаётся необязательной, а клиент тестируется без сессии.
- **`services/container.py` — единственное место сборки.** Обработчик получает
  готовый `Services`; тесты собирают тот же контейнер вокруг своей сессии, так что
  второй путь сборки не может разойтись с первым.

### Один запрос — одна транзакция

`DbSessionMiddleware` открывает сессию на апдейт, коммитит после обработчика и
откатывает при исключении. Обработчики, которые говорят пользователю
«сохранено», вызывают `services.commit()` **до** отправки ответа — иначе
пользователь увидит подтверждение, а коммит упадёт уже после.

### Таймзоны

Всё расписание считается в UTC. PostgreSQL хранит `timestamptz` и возвращает
смещение, SQLite его теряет — и naive-datetime, доехавший до планировщика,
падает `TypeError` ровно в момент ответа живого пользователя. Тип `UtcDateTime`
нормализует значения на входе и выходе, поэтому остальной код не знает, с какой
СУБД он разговаривает. Суточный лимит новых слов отсчитывается от полуночи в
таймзоне пользователя.

**Слово не выпадает на повторение в день добавления.** Первое повторение новой
карточки планируется на начало следующего дня в таймзоне пользователя, а не на
«сейчас»: слово добавляют, чтобы помнить его завтра, а не чтобы зазубрить в той же
сессии, где его напечатали. Полночь в таймзоне пользователя — заодно и момент,
когда сбрасывается суточный бюджет новых карточек, поэтому карточка не может
прийти раньше, чем на неё появится бюджет. Пустая очередь при этом не молчит:
экран «повторять» называет время, когда придёт ближайшая карточка, — и отвечает
тем же и на «позже», и на «всё повторено».

## Модель данных

```
users ─┬─ decks ── cards ── reviews
       ├─ streaks (1:1)
       └────────────┘
llm_calls (журнал обращений к модели)
```

- **`cards`** — содержимое (слово, перевод, транскрипция, часть речи, пример,
  заметки, теги, источник) **и** состояние памяти FSRS (`due_at`, `state`, `step`,
  `stability`, `difficulty`, `last_review_at`, `reps`, `lapses`).
- **`reviews`** — append-only журнал ответов. В `cards` лежит только текущее
  состояние; журнал позволяет считать статистику и позже переобучить параметры
  FSRS, не заставляя пользователя переучивать слова.
- **`llm_calls`** — сколько токенов, сколько миллисекунд, чем закончилось. Текст
  промпта и ответа пишутся только при `LOG_LLM_PAYLOADS=true`: там лежит всё, что
  напечатал пользователь. Метрики пишутся всегда — без них плохой разбор
  неотлаживаем, и на них же потом можно построить квоту на пользователя.

- **`streaks`** — серия, заморозки и счётчик пропусков, одна строка на
  пользователя. Отдельная таблица, а не колонки в `users`: это подсистема со
  своими правилами, и место для её роста (история заморозок, недельные цели не
  должны расширять строку, которую читает каждый запрос).
- **`decks.topic`** — домен, который колода сейчас собирает. Читается, когда
  просят «ещё слова» без темы.
- **`users.praise_history`** — JSON с индексами использованных шаблонов по
  банкам. Состояние представления, но принадлежит пользователю и обязано
  переживать перезапуск.
- **Настройки напоминаний — колонками в `users`**: три настройки и две суточные
  отметки, которые читает один периодический запрос. Серия уехала в свою таблицу,
  потому что у неё есть правила и она будет расти; здесь расти нечему, и join на
  каждом тике не окупился бы.

Уникальность: `(user_id, deck_id, term)` для карточек, `(user_id, name)` для
колод, `user_id` для серий. Все выборки карточек скоупятся по `user_id` внутри самого запроса, поэтому
устаревшая inline-кнопка не может дотянуться до чужих данных.

## LLM-слой

1. `MessageParser` решает, нужен ли вызов модели вообще.
2. `OpenAiCompatibleClient` запрашивает JSON (`response_format=json_object`),
   валидирует pydantic-схемой `ParseResponse`.
3. Невалидный ответ отправляется модели назад вместе с текстом ошибки — это чинит
   почти все проблемы формы. Транспортные ошибки ретраятся ограниченно; ошибка
   авторизации падает сразу, потому что повтор её не исправит.
4. Провайдер, не поддерживающий `response_format`, распознаётся по 400 и
   запрос повторяется без него — это нужно для Ollama и подобных серверов.
5. Если модель недоступна или упала — работает `FallbackParser`.

Незнакомый `intent` (`"greeting"`, `"save_word"`) не роняет разбор: он
приводится к `unknown`, потому что карточки в том же ответе могут быть верными.

## Напоминания

Решение «кому и когда» — снова чистая функция (`domain/reminders.py`) над
неизменяемым контекстом: часовой пояс, выбранные времена, вчерашние отметки,
сколько ждёт карточек, отвечено ли сегодня, жива ли серия.

**Тик, а не расписание.** Периодический обход спрашивает «кто сейчас должен
получить сообщение», а не ставит таймер на 09:00. Это даёт три вещи: бот,
лежавший в 09:00, отправит утреннее напоминание, поднявшись в 10:00; никто не
получит сообщение в 03:00 из-за уехавшего таймера; переход на летнее время
ничего не ломает, потому что сравнивается местный настенный час, а не смещение.

**Два сообщения, но не больше.** Утреннее уходит, только если есть что
повторять: «у вас нечего повторять» — это уведомление об отсутствии уведомления.
Вечернее — только пока серию ещё можно спасти (жива и сегодня не отвечено), и
оно несёт очередь с собой, поэтому бот, пролежавший весь день, отправит одно
сообщение, а не два. После вечернего утренний слот тоже считается закрытым.

**Один запрос-супермножество.** Точный фильтр «ещё не напоминали сегодня» требует
часового пояса каждого пользователя, а это в SQL переносимо не выражается.
Поэтому запрос берёт надмножество (`last_reminder_on IS NULL OR <= utc_today`), а
точное решение принимается в Python. Плата — повторный просмотр тех, кому уже
отправили; выигрыш — корректность на границах суток. Оптимизация (материализовать
«следующее напоминание в» по UTC) вынесена в следующие шаги, а не сделана вслепую.

**Никакого потолка на тик.** Обход всегда начинается с наименьшего id, поэтому
ограничение «не больше N пользователей за тик» навсегда замораживало бы всех
дальше N. `batch_size` задаёт размер одной порции, но обход идёт до конца.

**Недоставляемость — не то же самое, что сбой.** Заблокировавший бота получает
`is_blocked` и больше не тревожится: повторять бессмысленно. Транспортная ошибка
не ставит отметку, и следующий тик пробует снова. Разделение задано типами:
нотификатор бросает `RecipientUnreachable` для первого случая и что угодно другое
для второго.

Считающие запросы батчируются: `queue_counts` — один запрос на пачку,
`counts_since` — по одному на каждую встреченную границу суток (обычно две-три на
пачку, потому что пользователи сгруппированы по поясам). Иначе тик превратился бы
в N+1 на каждое уведомление.

**Два способа запуска.** По умолчанию тик живёт в процессе бота. Для нескольких
реплик есть `eng-remember-remind` — тот же обход одной командой, для cron; в этом
случае встроенный цикл надо выключить, иначе каждая реплика отправит своё.
Напоминания идемпотентны по дню, так что случайный двойной запуск не спамит.

## Подбор слов

Второй вызов модели, с другой задачей: парсер читает то, что написал
пользователь, а исследователь (`services/llm/explorer.py`) порождает слова,
которых в сообщении не было.

**Два шага, а не один.** Сначала `parse_message` определяет намерение и достаёт
тему, количество и слова-затравки. Потом, если намерение `expand`, вызывается
`expand_words`. Разделение стоит одного лишнего запроса, но даёт две вещи:
уточняющий вопрос задаётся до того, как потрачены токены на генерацию, и промпты
остаются короткими и предсказуемыми — генерирующий промпт не должен одновременно
ещё и классифицировать.

**Слово с контекстом и слова того же домена — одним сообщением.**
«Добавь arrangement как во фразе … и ещё пару слов на эту тему» — это два
намерения в одном сообщении, и выполняться должны оба. Разбор возвращает
`more_words`: карточки слова, домен (`topic`) и количество (`count`) приходят из
одного ответа модели, поиск идёт с этим словом как затравкой, и всё показывается
одним пакетом с одной кнопкой «Сохранить» — две отдельные кнопки подтверждения
разъезжались бы. Приложенная фраза служит дважды: задаёт смысл для перевода
(«здесь arrangement — упорядоченный набор, а не договорённость») и подсказывает
домен. Если домен не читается ни из слова, ни из контекста, бот спрашивает тему:
слово можно сохранить сразу, а слова по многозначному слову без домена —
угадывание. Кнопка «🔄 Ещё слова» заменяет только найденную половину пакета,
слово пользователя с кнопки не пропадает. Сбой или пустой результат поиска не
отменяет первую половину: слово остаётся подтверждаемым, а причина видна
пометкой под ним.

**Модель предлагает, сервис распоряжается.** `services/discovery.py` проверяет
то, чего модель знать не может:

- слова, которые у пользователя уже есть, отбрасываются точно (`all_terms`), а
  не приблизительно;
- если был дан исходный текст, предложение обязано в нём встречаться. Проверка
  идёт по четырёхбуквенному стему, поэтому «run» принимается для «running» и
  наоборот. Нерегулярные формы («go»/«went») проверку не проходят и
  отбрасываются — это выбранное направление ошибки: слово, которого в тексте
  нет, хуже, чем слово, которого не хватает до запрошенного числа;
- результат обрезается до запрошенного количества.

Обе проверки только удаляют, поэтому у модели запрашивается больше с запасом
(`DISCOVERY__OVERSAMPLE`). Отброшенное показывается пользователю: молча выдать
шесть слов вместо десяти выглядит как сбой, а «отсеяно 4 — этих слов нет в
тексте» читается как забота.

**Уточнения.** Схема ответа умеет вернуть `clarification` с вопросом и 2–4
вариантами. Варианты становятся кнопками, но текст варианта в callback не
уезжает — он лежит в FSM, поэтому длинный вариант не упрётся в лимит Telegram, а
устаревшая кнопка отсекается проверкой индекса. Уточнение задаётся только когда
действовать нечем: темы нет, текста нет, и колода ничего не помнит. Число
раундов ограничено (`DISCOVERY__MAX_CLARIFICATION_ROUNDS`), иначе модель,
повторяющая один и тот же вопрос, заперла бы диалог.

Кнопка «🤷 Реши сам» всегда есть и всегда последняя: вынужденный выбор хуже
чуть более общей подборки. Она опирается на тему, запомненную в колоде, — ровно
поэтому колода её и хранит.

**Где живёт тема.** `decks.topic` обновляется при сохранении подборки. Тема из
колоды подставляется только когда в запросе нет ни своей темы, ни текста:
старая тема рядом со свежим абзацем увела бы подборку в сторону.

## Серии, пропуски, заморозки

Правила — чистые функции в `domain/gamification.py` над неизменяемым
`StreakState`, как и планировщик FSRS. Ни одна из них не читает часы: вызывающий
передаёт локальную дату, поэтому «заморозка закрыла пропуск» и «серия
прервалась» проверяются тестом с явной датой, без базы и без бота.

- **День засчитывается первым же ответом.** Порог намеренно низкий: механика
  про возвращение каждый день, а не про объём.
- **Заморозка** закрывает один пропущенный день. Новая даётся за каждые
  `STREAK__FREEZE_EVERY_DAYS` дней подряд, сверх `STREAK__FREEZE_MAX` не
  копится. Сравниваются частные (`after // n > before // n`), а не остаток: так
  серия, прерванная и отстроенная заново, зарабатывает заморозку снова — иначе
  долгое отсутствие навсегда лишало бы механики.
- **Новичку выдаётся одна заморозка сразу.** Механика невидима, пока не спасёт
  серию; ждать её неделю — значит неделю не давать о ней узнать.
- **Пропуски** считаются в `missed_days` и показываются в статистике.

Важная деталь — поле называется `accounted_on`, а не «последняя активность»: это
последний день, который состояние уже учло. Так `roll_forward` становится
идемпотентным, и это не педантизм — функция вызывается и на чтении (`/stats`,
`/start`), и на записи. Без этого счётчик пропусков раздувался бы при каждом
открытии статистики; тест на идемпотентность это и поймал.

## Похвала

Банк и правило выбора — в `domain/praise.py`. Пять банков: `good` (45), `easy`
(25), `hard` (25), `again` (25) и `milestone` (20) — 140 шаблонов.

Выбор работает как перемешанный мешок, а не как случайный тык: каждый шаблон
используется один раз, прежде чем хоть один повторится, а шаблон, закрывший
цикл, исключается из начала следующего. Единственное место, где повтор мог бы
проскочить, — стык двух циклов, и оно закрыто. История хранится в
`users.praise_history` (JSON), то есть переживает перезапуск; хранилище в памяти
дало бы повторы после каждого деплоя.

Две вещи, которые пришлось решить:

- **`again` — не похвала.** Слово забыто, ничего хорошего не произошло, поэтому
  там отдельный банк поддержки. Поздравление с промахом читается как
  невнимательность.
- **Ни один шаблон не обращается к пользователю в мужском роде** — бот не знает
  пола. Тест ищет глаголы прошедшего времени и гендерные комплименты регуляркой;
  он поймал три таких шаблона.

Похвала идёт первой строкой, расписание — второй, курсивом. Приятная фраза — то, что делает нажатие осмысленным, интервал —
справочная информация.

## Обработка ошибок

- Иерархия исключений от `EngRememberError` — на границе (глобальный обработчик)
  можно отличить инфраструктурный сбой от доменного.
- Любое необработанное исключение в обработчике попадает в `errors`-роутер:
  логируется с трейсбеком, пользователь получает одну фразу, апдейт помечается
  обработанным (иначе битый обработчик превращается в бесконечный ретрай).
- Неизвестная команда получает ответ, а не тишину.
- Отсутствие `BOT_TOKEN` — понятное сообщение и код выхода 2, а не трейсбек.

## Тестирование

286 тестов, четыре уровня:

| Уровень | Что покрывает |
|---|---|
| Домен | Интервалы FSRS, лапсы, превью оценок; серии, заморозки, идемпотентность; глубина банков похвал и отсутствие повторов; кто и когда получает напоминание, включая границы суток и переход на летнее время. Без базы и бота. |
| Юниты | Парсеры, схемы, клиент LLM (фейковый провайдер: ретраи, repair, отсутствие JSON-режима), подбор слов (дедуп, проверка по тексту, лимиты), репозитории, сервисы. |
| Сквозные | Настоящий диспетчер, настоящая БД, подменена только отправка в Telegram: `/start`, разбор текста, подтверждение, подбор по теме и из текста, диалог уточнений, повторение, похвала, серии, `/remind`, доставка напоминаний, экранирование HTML, заблокированный пользователь. |
| Интеграция | То, в чём SQLite расходится с Postgres: `timestamptz`, `json`, `date`, CHECK-ограничения, каскады. Запуск — `make test-integration`. |

Для LLM-путей есть `ScriptedClient`: подставной клиент, ответы которого тест
выписывает заранее, с диспетчеризацией по запрошенной схеме. Это делает
многошаговые сценарии — распознавание намерения, уточнение, генерация —
проверяемыми без сети и без ключа, и при этом лишний вызов модели не остаётся
незамеченным.

Тесты нашли девять реальных дефектов: regex-фолбэк съедал слово в паре,
отложенная новая карточка тут же возвращалась в очередь, пустые строки от модели
не становились `None`, naive-datetime из SQLite падал бы на первом же ответе
живого пользователя, обработчик «неизвестной команды» перехватывал `/add`,
`roll_forward` раздувал счётчик пропусков при каждом открытии статистики, три
шаблона похвалы обращались к пользователю в мужском роде, а потолок на число
пользователей за тик навсегда замораживал бы всех дальше этого числа.

Миграции проверяются отдельно: `alembic check` сверяет модели со схемой, а
`make migrate`/`downgrade base`/`upgrade head` прогоняются как round-trip. Один
дефект поймал и здесь: колонка `users.praise_history` добавлялась как NOT NULL
без значения по умолчанию, что падает на непустой таблице. Теперь она
добавляется в три шага — nullable, backfill, NOT NULL; а серверный дефолт убран
сознательно, потому что в Postgres у `json` нет оператора равенства и
`alembic check` на нём ломается.

## Конфигурация

Всё в переменных окружения, вложенность через `__` (`LLM__API_KEY`,
`SRS__DESIRED_RETENTION`). Полный список — в `.env.example`. Рабочие значения по
умолчанию есть у всего, кроме `BOT_TOKEN`.

Смысл основных настроек:

- `SRS__DESIRED_RETENTION` — целевая вероятность вспоминания (0.9 по умолчанию).
  Выше значение → короче интервалы, больше работы, лучше удержание.
- `SRS__ENABLE_FUZZING` — небольшой разброс интервалов, чтобы выученные вместе
  слова не ходили всю жизнь одной пачкой.
- `BOT__NEW_CARDS_PER_DAY` — бюджет новых карточек в день; переопределяется
  пользователем командой `/limit`.
- `LLM__RETRIES` — сколько дополнительных попыток после невалидного ответа.
- `STREAK__FREEZE_EVERY_DAYS` — за сколько дней подряд даётся заморозка; 0
  отключает начисление.
- `DISCOVERY__MAX_CLARIFICATION_ROUNDS` — сколько раз бот может переспросить,
  прежде чем действовать с тем, что есть.
- `DISCOVERY__CONTEXT_TEXT_MIN_LENGTH` — с какой длины сообщение считается
  исходным текстом, а не темой.
- `REMINDERS__TICK_SECONDS` — как часто бот проверяет, кому пора напомнить.
- `REMINDERS__DEFAULT_TIME` / `REMINDERS__DEFAULT_STREAK_TIME` — времена по
  умолчанию; пользователь, не трогавший настройку, следует за ними.

## Эксплуатация

- `make db-up && make migrate && make run` — полный локальный цикл.
- Миграции — отдельный шаг, контейнер при старте схему не меняет.
- Напоминания рассылает сам бот. Несколько реплик — выключить
  `REMINDERS__ENABLED` и повесить `eng-remember-remind` на cron.
- Логи структурированные (structlog); aiogram/SQLAlchemy замкнуты на тот же вывод.
- Хранилище FSM — в памяти процесса. Для одного воркера этого достаточно:
  теряется только ожидающее подтверждения сообщение. Переход на Redis — правка
  одной строки в `bot/dispatcher.py`.

## Что сознательно не сделано

- **Озвучка слов** — нужен внешний сервис или предзапись аудио.
- **Импорт/экспорт колод** (CSV, Anki `.apkg`) — отдельный сценарий с собственным
  форматом.
- **Несколько колод в интерфейсе** — модель готова, команды создания и
  переключения не написаны: сейчас всё пишется в колоду по умолчанию, и тема
  хранится там же.
- **Пропуск напоминания при нескольких репликах** — встроенный цикл отправляет
  из каждого процесса. Для этого есть `eng-remember-remind` и `cron`; блокировка
  в БД, чтобы работало без внешнего планировщика, не сделана.
- **Тренировка письма и аудирования** — другой тип карточек.
- **Общий Redis-стор FSM и несколько воркеров** — преждевременно до нагрузки.
- **Ручное управление заморозками** (купить, применить, отменить) — сейчас они
  начисляются и тратятся автоматически: так меньше решений, которые надо
  объяснять пользователю.
- **Дневная норма как условие серии** — день засчитывается с одного ответа;
  поднять порог — одна строка в правилах, но сначала надо понять, нужен ли он.

## Следующие шаги

1. Материализовать «следующее напоминание в» по UTC в отдельной колонке, чтобы
   тик не просматривал заведомо не готовых. Сейчас это осознанная плата за
   корректность на границах суток.
2. Колоды: создание, переключение, перенос карточек, тема на колоду вместо
   одной общей.
3. Экспорт колоды в CSV.
4. Метрики: сколько карточек в день, сколько лапсов, кривая удержания,
   распределение оценок; отдельно — сколько напоминаний доходит.
5. Подбор параметров FSRS по журналу `reviews` под конкретного пользователя.
6. Более длинный диалог: сейчас уточнение одношаговое, а «найди слова вот в этом
   тексте, но не про финансы» требует двух.
7. Блокировка на уровне БД для запуска нескольких реплик без внешнего cron.
