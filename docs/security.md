# Безопасность: лимиты, мониторинг, инциденты

Короткий операционный документ. Модель угроз — Telegram-бот для одного
пользователя на аккаунт: посторонний попадает в систему только через
собственный Telegram-аккаунт, но его сообщения уходят в LLM и хранятся в БД,
а модель — источник недостоверного текста.

## Что закрыто детерминированно

- Вывод модели не исполняется и не превращается в SQL: клиент возвращает
  Pydantic-схему (`services/llm/schema.py`), SQL — только ORM с bind-параметрами.
- Все строки модели прогоняются через `flatten_line` (одна строка, лимит длины,
  без `<>` для значений, попадающих в промпт), поэтому сохранённая тема колоды
  не может разорвать обёртку `<topic>` в следующем запросе.
- Любой текст, уходящий в Telegram как HTML, экранируется в `bot/texts.py`.
- Все выборки из БД скоупятся `user_id`; владелец карточки проверяется в
  callback-обработчиках.
- Расход на модель ограничен на пользователя до вызова в скользящем окне
  24 часа: `LLM__MAX_CALLS_PER_DAY` (60 интерактивных),
  `LLM__MAX_EXAMPLE_CALLS_PER_DAY` (30 на генерацию примеров) и
  `LLM__MAX_TOKENS_PER_DAY` (100 000). Общий бюджет бота —
  `LLM__MAX_TOKENS_PER_DAY_GLOBAL` (2 000 000): на
  `LLM__GLOBAL_ALERT_PERCENT` (80%) пишется предупреждение и уходит алерт
  админу, на 100% модельные вызовы отключаются, парсер уходит в правила.
  Реализация — `services/llm/quota.py` и `services/llm/budget.py`. При
  исчерпании глобального бюджета парсер уходит в правила, подбор слов сообщает
  о недоступности модели, а проверка ответов работает по точному совпадению.
- Модельные вызовы одного пользователя сериализуются: per-user lock в
  `services/llm/quota.py` не даёт двум запросам пересечься, а
  `BOT__TASKS_CONCURRENCY_LIMIT` (20) ограничивает общее число одновременных
  апдейтов на процесс. Это не даёт всплеску сообщений обойти квоту и занять
  все слоты бота.
- Входящий поток ограничен на пользователя: `BOT__MESSAGES_PER_MINUTE` (10)
  и `BOT__CALLBACKS_PER_MINUTE` (30). Одинаковый plain-text в течение
  `BOT__DUPLICATE_MESSAGE_TTL_SECONDS` (60 секунд) второй раз не обрабатывается.
  Guard'ы живут в `bot/middlewares/rate_limit.py` и `bot/middlewares/dedup.py`.
- Индекс `llm_calls(user_id, created_at)` держит квотные запросы быстрыми;
  старый индекс по `created_at` остаётся для глобальных отчётов.

## Что логируется

- Таблица `llm_calls`: кто (`user_id`), зачем (`purpose`), модель, попытка,
  токены, латентность, признак успеха и текст ошибки. Пишется всегда.
  Тексты запроса и ответа — только при `LOG_LLM_PAYLOADS=true` (по умолчанию
  выключено: там всё, что набрал пользователь).
- structlog, JSON при `LOG_JSON=true` (по умолчанию). События для алертов:

| Событие | Где | Что значит |
|---|---|---|
| `llm_quota_exceeded` | services/llm/quota.py | аккаунт упёрся в лимит — аномалия или злоупотребление |
| `llm_global_budget_warning` / `llm_global_budget_exceeded` | services/llm/budget.py | глобальный бюджет на 80% / 100% |
| `llm_budget_alert_failed` | services/llm/budget.py | не удалось отправить алерт админу |
| `rate_limit_exceeded` | bot/middlewares/rate_limit.py | пользователь превысил 10 сообщений или 30 нажатий в минуту |
| `duplicate_message_ignored` | bot/middlewares/dedup.py | повтор одинакового текста внутри TTL |
| `discovery_out_of_text` | services/discovery.py | модель выдумывает слова «из текста» — деградация качества |
| `llm_parse_failed` | services/llm/parser.py | разбор ушёл в правила: сбой провайдера или ответ вне схемы |
| `discovery_failed` / `discovery_quota_exceeded` | bot/routers/capture.py | подбор слов не удался, пользователь получил отказ |
| `handler_failed` | bot/routers/errors.py | необработанное исключение, есть traceback |
| `reminder_failed` / `reminder_unreachable` | services/reminders.py | напоминание не доставлено |
| `blocked_user_ignored` | bot/middlewares/user.py | пишет заблокированный аккаунт |

Минимальный алерт: непустой поток `llm_quota_exceeded` и `handler_failed`.

## Runbook

1. **Подозрение на утечку `BOT_TOKEN`** — отозвать через @BotFather, обновить
   `.env`, перезапустить. Токен живёт только в памяти процесса и в `.env`.
2. **Подозрение на утечку ключа LLM** — отозвать ключ у провайдера, выпустить
   новый, обновить `LLM__API_KEY`. Аудит расходов — по `llm_calls`.
3. **Злоупотребление (разгон стоимости)** — посмотреть, кто жжёт бюджет:

   ```sql
   SELECT user_id, count(*) AS calls, sum(total_tokens) AS tokens
   FROM llm_calls
   WHERE created_at >= now() - interval '1 day'
   GROUP BY user_id ORDER BY tokens DESC;
   ```

   Дальше: снизить лимиты (`LLM__MAX_*`), при необходимости заблокировать
   аккаунт — `UPDATE users SET is_blocked = true WHERE telegram_id = <id>;`.
4. **Странный ответ модели** — включить `LOG_LLM_PAYLOADS=true` на время
   разбора, затем выключить: в `llm_calls` начнут писаться тексты пользователя.

## Хранение и приватность

- `llm_calls` хранит метрики бессрочно; тексты — только при включённом
  `LOG_LLM_PAYLOADS`. Если включали, почистите:
  `UPDATE llm_calls SET request_text = NULL, response_text = NULL;`.
- Промпты содержат только данные самого пользователя: его сообщение, его
  термины, тема его колоды. Чужие данные в промпт не попадают.

## Сознательно принятые риски

- Вывод модели не сканируется на PII/секреты: он уходит только автору запроса,
  наружу (в веб/файлы) не публикуется.
- Квота и глобальный бюджет считаются по закоммиченным строкам `llm_calls`.
  Per-user lock сериализует вызовы, но при всплеске обновлений возможен
  небольшой перерасход до коммита; для жёсткого потолка нужна атомарная
  резервация в БД или Redis. При нескольких репликах каждый процесс считает
  лимит и держит свой lock отдельно.
- Роль БД одна (владелец своей схемы): приложение по своей природе пишущее,
  read-only роль сломала бы основной сценарий. Митигация — non-root пользователь
  в контейнере и один том Postgres.
