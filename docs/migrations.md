# Миграции: правила и приёмы

Документ для того, кто добавляет ревизию. Деплой и бэкапы — в
[deploy.md](deploy.md); здесь только схема и данные.

## Что уже делает `alembic/env.py`

- **Одна ревизия — одна транзакция.** В `context.configure` включён
  `transaction_per_migration=True`: упавшая ревизия откатывается целиком, а
  предыдущие остаются применёнными — ровно так, как записано в
  `alembic_version`. Долгий прогон из десяти ревизий не держит блокировки на
  всех таблицах сразу.
- **Один мигратор за раз.** В online-режиме PostgreSQL `env.py` берёт
  session-level `pg_advisory_lock` с константным ключом и отпускает его в
  `finally`. Второй `alembic upgrade` (перезапуск `migrate` в compose, деплой
  поверх cron-задачи) ждёт, а не интерливит DDL. Если процесс убили,
  PostgreSQL снимает блокировку вместе с соединением; для ручной проверки:

  ```sql
  SELECT pid, classid, objid, granted FROM pg_locks WHERE locktype = 'advisory';
  ```

  SQLite блокировку пропускает: там нет ни advisory locks, ни конкурентных
  писателей, против которых она нужна.
- **URL — только из настроек.** `alembic.ini` не содержит `sqlalchemy.url`:
  миграция не может уйти не в ту базу, в которую ходит бот.

## Правила

### DDL и backfill — разные ревизии

Схема меняется быстро, данные — медленно. Одна ревизия, которая и добавляет
колонку, и наполняет её, держит транзакцию на всё время наполнения: блокировки,
рост WAL, невозможность откатиться до конца backfill'а, не потеряв DDL.

Порядок:

1. Ревизия только со схемой (nullable-колонка, новая таблица, индекс).
2. Выкладка кода, который умеет и со старыми, и с новыми данными.
3. Ревизия только с backfill'ом.
4. Отдельная ревизия с `NOT NULL`/`UNIQUE`/удалением старой колонки — когда
   предыдущая версия кода уже не в проде.

### Backfill — батчами по диапазонам id

`UPDATE` по всей таблице — это одна транзакция на миллион строк и WAL на весь
объём. Идти надо страницами по первичному ключу, фиксируя каждую страницу:

```python
def upgrade() -> None:
    bind = op.get_bind()
    cursor, batch = 0, 1000
    while True:
        ids = bind.execute(
            sa.text(
                "SELECT id FROM cards WHERE language IS NULL AND id > :after "
                "ORDER BY id LIMIT :limit"
            ),
            {"after": cursor, "limit": batch},
        ).scalars().all()
        if not ids:
            break
        bind.execute(
            sa.text("UPDATE cards SET language = 'en' WHERE id = ANY(CAST(:ids AS integer[]))"),
            {"ids": ids},
        )
        bind.commit()  # каждая пачка — своя транзакция
        cursor = ids[-1]
```

Курсор — именно id, а не `OFFSET`: `OFFSET` перечитывает и пересортировывает
всё, что уже пройдено, и на большой таблице деградирует квадратично. Условие
`WHERE ... IS NULL` при этом сохраняется, поэтому повторный запуск после
падения продолжает с места, а не начинает заново.

### Индексы на больших таблицах — `CONCURRENTLY` и `autocommit_block`

Обычный `CREATE INDEX` блокирует запись в таблицу на всё время построения.
Для таблиц, которые уже наполнены в проде:

```python
def upgrade() -> None:
    with op.get_context().autocommit_block():
        op.create_index(
            "ix_cards_due_at",
            "cards",
            ["due_at"],
            postgresql_concurrently=True,
        )
```

`autocommit_block()` нужен потому, что `CONCURRENTLY` нельзя выполнять внутри
транзакции — в том числе внутри транзакции одной ревизии. В этом блоке нельзя
делать ничего другого: всё, что попадёт внутрь, тоже выполнится без
транзакции. Если построение упало, индекс остаётся невалидным — его надо
удалить (`DROP INDEX CONCURRENTLY`) и повторить, а не «дописывать» ревизию.

На пустой базе (CI, локальная разработка) тот же код работает: `CONCURRENTLY`
там просто не нужен, но безвреден.

### Разрушающий downgrade — в докстринге ревизии

Откат может быть необратимым: колонку можно удалить, а данные из неё — нет.
Молчаливый `downgrade`, который теряет строки, хуже, чем честный докстринг.
Правило: если откат удаляет или переписывает данные, это написано в докстринге
ревизии, а сам `downgrade` делает ровно то, что обещает:

```python
"""Add per-direction cards.

Revision ID: 264f4235eef5
"""

def downgrade() -> None:
    # The 3-column unique constraint cannot be recreated while both directions
    # of a word exist: drop the reverse twins first. Rolling back to a
    # pre-pairs schema cannot keep data that schema has no place for.
    op.execute("DELETE FROM cards WHERE direction = 'reverse'")
    ...
```

Докстринг читают во время инцидента, когда откат уже запускают, — поэтому он
пишется для оператора, а не для автора.

### Совместимость со старой версией кода

Пока идёт выкладка, рядом работают старый и новый процесс на одной схеме.
Поэтому:

- новая колонка сначала `nullable` или с `server_default`, `NOT NULL` — потом;
- переименование — это «добавить новую, написать в обе, удалить старую», три
  ревизии, а не `ALTER ... RENAME`;
- удаление колонки/таблицы — отдельная ревизия после того, как код перестал на
  них ссылаться.

### Разрушающие изменения и SQLite

Локальные тесты идут на SQLite, где `ALTER TABLE` почти ничего не умеет.
`render_as_batch=True` в `env.py` переписывает таблицу целиком, но только для
операций, которые alembic умеет разложить на batch. Полная цепочка ревизий на
SQLite исторически не проигрывается (в ней есть `ALTER ... SET NOT NULL` без
batch), поэтому локальная разработка схемы идёт против PostgreSQL из
`docker compose`, а SQLite остаётся базой юнит-тестов, которые создают схему
через `create_all`. Если ревизия рассчитана на PostgreSQL-специфику
(`CONCURRENTLY`, `USING`, частичные индексы), это указывается в докстринге — и
проверяется на PostgreSQL, а не только локально.

### Autogenerate — черновик, а не результат

`make revision m="..."` даёт заготовку. Перед коммитом:

- прочитать diff: alembic не видит переименований и предложит `drop` + `add`;
- проверить, что типы отрендерились как `sa.DateTime(timezone=True)`, а не как
  импорт из `eng_remember` (`render_item` в `env.py` для этого и нужен);
- пустая миграция — сигнал, что модель и схема разошлись не там, где кажется;
- `make migrate-check` (`alembic check`) должен сказать
  `No new upgrade operations detected`.

## Чек-лист перед merge

```bash
make migrate                                        # upgrade head
make migrate-check                                  # модели и миграции согласны
make downgrade && make migrate                      # откат и повторный накат
uv run alembic upgrade head                         # повторный накат идемпотентен
```

CI прогоняет то же самое: `upgrade head` дважды, `alembic check`, раундтрип
`downgrade -1 && upgrade head` на служебной базе джоба. Ревизия, которая
проходит локально, но не переживает откат, ломает CI, а не прод.

## Если миграция уже идёт и что-то пошло не так

- Не запускать второй `alembic upgrade` «на всякий случай»: он встанет в
  очередь за advisory lock и ничего не ускорит.
- Посмотреть, на какой ревизии база: `docker compose run --rm migrate alembic current`.
- Упавшая ревизия откатилась целиком (`transaction_per_migration`), поэтому
  лечится исправлением ревизии и повторным запуском, а не ручным добиванием
  полуприменённой схемы. Исключение — ревизия с коммитами по пачкам (backfill):
  применённые пачки остаются, а повторный запуск продолжает с курсора; именно
  поэтому условие `WHERE ... IS NULL` в таких ревизиях обязательно.
- `downgrade` с разрушающими изменениями — только после бэкапа
  ([deploy.md](deploy.md#бэкап-и-восстановление)).
